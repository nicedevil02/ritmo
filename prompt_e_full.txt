قوانین غیرقابلمذاکره:

5. اگر واقعیت کد با چیزی که این پرامپت ادعا کرده **مغایر** بود: **ویرایش نکن، متوقف شو، گزارش بده.** حدس نزن.

7. `catch (_) {}` جدید **ننویس**. هر catch باید حداقل `RitmoLogger.error(...)` داشته باشد.
8. پیامهای کاربر همه فارسی هستند. متن انگلیسی به UI اضافه نکن.

### E-1 — رفع dead-lock در تیکزدن مستحبات ← MU-24

**فایل:** `lib/core/domain/agenda/agenda_action_handler.dart`

**تابع:** `toggleAgendaItem`

**مشکل اثباتشده:** شاخهی `AgendaDomain.mustahab` **داخل** `await db.transaction((txn) async { ... })` قرار دارد، ولی بهجای `txn` از `WorshipEngine.instance.logDone` استفاده میکند که خودش `DatabaseHelper.instance.database` میگیرد و `db.transaction` تازه باز میکند. در sqflite این یعنی: تراکنش بیرونی قفل را نگه داشته و منتظر تراکنش درونی است، تراکنش درونی منتظر آزاد شدن قفل است → **قفل ابدی**. این استثنا پرتاب نمیکند، فقط برای همیشه hang میکند و کل دیتابیس اپ تا ریاستارت از کار میافتد.

**کاری که باید بکنی:** فراخوانی worship را **از داخل تراکنش بیرون بکش**.

قبل:

```dart
await db.transaction((txn) async {
  if (item.domain == AgendaDomain.course) {
    ...
  } else if (item.domain == AgendaDomain.mustahab) {
    if (isDone) {
      final date = DateTime.tryParse(item.dateStr) ?? DateTime.now();
      await WorshipEngine.instance.logDone(practiceId: item.sourceId, date: date);
    } else {
      final date = DateTime.tryParse(item.dateStr) ?? DateTime.now();
      await WorshipEngine.instance.clearLog(practiceId: item.sourceId, date: date);
    }
  }
});
```

بعد:

```dart
// mustahab را خارج از تراکنش هندل میکنیم؛ WorshipEngine خودش تراکنش خودش را باز میکند.
if (item.domain == AgendaDomain.mustahab) {
  final date = DateTime.tryParse(item.dateStr) ?? DateTime.now();
  final result = isDone
      ? await WorshipEngine.instance.logDone(
          practiceId: item.sourceId,
          date: date,
          amount: _resolveToggleAmount(item, isDone: true), // ← E-5
        )
      : await WorshipEngine.instance.clearLog(
          practiceId: item.sourceId,
          date: date,
        );

  if (result is WorshipLogFailed) {                       // ← E-6 (MU-28)
    RitmoLogger.error(
      '[AgendaActionHandler] mustahab toggle failed: ${result.error}',
    );
  }

  _invalidateAndNotify(item.dateStr, 'WorshipUpdated', {
    'date': item.dateStr,
    'practiceId': item.sourceId,
    'isDone': isDone,
  });
  return;                                                  // ← از تابع خارج شو
}

await db.transaction((txn) async {
  if (item.domain == AgendaDomain.course) {
    ...
  }
  // شاخهی mustahab اینجا دیگر نباید وجود داشته باشد
});
```

**نکات که فراموش نکنی:**

- شاخهی `mustahab` را از داخل `db.transaction` **کاملاً پاک کن** — نگذار کپیاش بماند.
- `import 'package:ritmo/core/logging/ritmo_logger.dart';` را اضافه کن اگر نیست.
- بعد از `return`، بلوک `_invalidateAndNotify` انتهای تابع برای mustahab اجرا نمیشود؛ به همین دلیل قبل از `return` صداش زدیم. **این را حذف نکن.**
- همین بررسی «تراکنش تودرتو» را برای شاخههای `course` / `goalStep` / `worshipDebt` هم انجام بده: آنها از `txn` استفاده میکنند و سالماند — **دست نزن**.

### E-2 — افزودن تیک به آیتمهای قرآن/ذکر در اجندا ← MU-1

> ⛔ فقط بعد از تمامشدن E-1.
> 

**فایل:** `lib/core/domain/agenda/quran_dhikr_agenda_renderer.dart`

**مشکل:** این رِندِرِر پارامتر `onChanged` را میپذیرد ولی **هیچوقت صدایش نمیزند**؛ `onTap` هم فقط `Navigator.pushNamed(context, '/worship')` میکند. یعنی کاربر برای تیکزدن یک ذکر مجبور است از اجندا خارج شود. این دقیقاً همان چیزی است که مالک پروژه در مورد «نمایش مستحبات برنامهریزیشده با قابلیت تیک» تأیید کرده بود.

**کاری که باید بکنی:**

1. یک ویجت تیک (`Checkbox` یا همان استایلی که `DefaultAgendaRenderer` استفاده میکند) به ابتدای ردیف اضافه کن. **دقیقاً از همان کامپوننت و همان اندازه/رنگ `DefaultAgendaRenderer` استفاده کن** تا ظاهر اجندا یکدست بماند — کامپوننت جدید نساز.

### E-3 — حذف فیلتر `reminderEnabled` از ساخت اجندا ← MU-2

**فایل:** `lib/core/domain/agenda/day_agenda_service.dart` → `_buildContext`

**مشکل:** مستحبات فقط وقتی وارد اجندا میشوند که `p['reminderEnabled'] == 1`. یعنی کاربری که فقط **نوتیفیکیشن** یک ذکر را خاموش میکند، آن ذکر را از **برنامهی روزش** هم حذف میکند — بیهیچ هشداری. برای نمازها چنین فیلتری وجود ندارد؛ این ناسازگاری منطقی است.

**کاری که باید بکنی:** شرط را به این تغییر بده:

```dart
// قبل
(type == 'MUSTAHAB' || type == 'QURAN' || type == 'DHIKR') && p['reminderEnabled'] == 1

// بعد
(type == 'MUSTAHAB' || type == 'QURAN' || type == 'DHIKR')
```

**حضور در اجندا = `isActive = 1 AND userDisabledAt IS NULL`** (این در E-4 اعمال میشود). `reminderEnabled` از این به بعد **فقط** معنی «نوتیفیکیشن بفرست یا نه» را دارد.

**فراموش نکن:** بعد از این تغییر، `reminderEnabled` نباید در **هیچ** مسیر ساخت اجندا استفاده شود. `grep -rn "reminderEnabled" lib/core/domain/agenda/` بگیر و تأیید کن که خالی است.

### E-4 — یکسانسازی سه خوانندهی `worship_practices` ← MU-15 + MU-27

**مشکل اثباتشده:** الان **سه** جای مختلف همین جدول را با **سه شرط متفاوت** میخوانند:

| خواننده | شرط | مرتبسازی |
| --- | --- | --- |
| `WorshipEngine.loadDay` | `isActive = 1 AND (userDisabledAt IS NULL)` | `sortOrder ASC` |
| `DayAgendaService._buildContext` | `isActive = 1`  • فیلتر `reminderEnabled` | ❌ ندارد |
| `WorshipAgendaSource.load` (مرده) | `practiceType != 'PRAYER'` — **بدون هیچ فیلتر فعالبودن** | ❌ ندارد |

نتیجه: صفحهی عبادت یک مجموعه نشان میدهد، اجندا مجموعهای دیگر، و اگر روزی `WorshipAgendaSource.load` زنده شود، عبادتهای غیرفعال و بدهیهای بایگانیشده ناگهان ظاهر میشوند.

**کاری که باید بکنی:**

1. در `lib/features/worship/logic/worship_engine.dart` یک ثابت عمومی اضافه کن:

```dart
/// تنها شرط معتبر برای «این عبادت باید دیده شود».
/// هر خوانندهی جدید worship_practices موظف است از همین استفاده کند.
static const String activePracticesWhere =
    'isActive = 1 AND userDisabledAt IS NULL';
static const String activePracticesOrderBy = 'sortOrder ASC, id ASC';
```

1. در `DayAgendaService._buildContext` کوئری `worship_practices` را به همین `where` و همین `orderBy` تغییر بده.
2. در `WorshipAgendaSource.load` هم همین را اعمال کن، **و** فیلتر بدهی را اضافه کن: `worship_debts` باید `where: 'isArchived = 0 AND remainingCount > 0'` بخورد (الان کل جدول را بیفیلتر میخواند).
3. در `WorshipEngine.loadDay` رشتهی درون کد را با همین ثابت جایگزین کن (رفتار عوض نمیشود، فقط تکمنبع میشود).
4. `try/catch` فعلی `loadDay` که در صورت نبود ستون `userDisabledAt` به شرط سادهتر سقوط میکند را **نگه دار** — ولی در `catch` یک `RitmoLogger.warning` اضافه کن.

**⚠️ هشدار ترتیبی که حتماً باید بخوانی:** پرامپت D قرار است `WorshipAgendaSource` را بهعنوان منبع زندهی اجندا فعال کند. **اگر E-4 قبل از D اجرا نشود، D یک رگرسیون قابلمشاهده میسازد** (عبادتهای غیرفعال + بدهیهای تسویهشده در اجندا ظاهر میشوند). E-4 پیشنیاز D است.

### E-5 — شمارش، هدف روزانه و حلقهی «تیک نمیچسبد» ← MU-3 + MU-19

**مشکل اثباتشده (بدتر از چیزی که قبلاً گزارش شده بود):**

- `WorshipEngine.logDone` امضایش `{required practiceId, required date, int amount = 1}` است و مینویسد:
    
    `resultType: amount >= dailyTarget ? 'DONE' : 'PARTIAL'`
    
- `toggleAgendaItem` همیشه با `amount` پیشفرض (=۱) صدا میزند.
- `WorshipDayStatus.isDone => resultType == 'DONE'`

پس برای یک عبادت با `dailyTarget = 3`:

تپ کاربر → `amount=1` → `resultType='PARTIAL'` → اجندا `isDone=false` میبیند → **تیک بلافاصله برمیگردد**. کاربر هرچقدر بزند، هیچوقت DONE نمیشود. **این یک باگ حلقهی بینهایت قابلمشاهده است.**

ضمناً هر تپ `countDone` را روی `amount` **بازنویسی** میکند، نه افزایش — پس شمارش تسبیح هم هیچوقت بالا نمیرود.

**کاری که باید بکنی — هر سه قسمت، هیچکدام را جا نینداز:**

**۵-الف) `logDone` را افزایشی کن.** در `lib/features/worship/logic/worship_engine.dart`:

```dart
Future<WorshipLogResult> logDone({
  required String practiceId,
  required DateTime date,
  int amount = 1,
  bool increment = false,   // ← جدید: true یعنی به مقدار قبلی اضافه کن
}) async {
```

داخل تراکنش، قبل از insert:

```dart
var effectiveAmount = amount;
if (increment) {
  final prev = await txn.query(
    'worship_completions',
    columns: ['countDone'],
    where: 'id = ?',
    whereArgs: [recordId],
    limit: 1,
  );
  final prevDone = prev.isNotEmpty ? (prev.first['countDone'] as int? ?? 0) : 0;
  effectiveAmount = prevDone + amount;
}
if (effectiveAmount > dailyTarget) effectiveAmount = dailyTarget;
```

و در `completionRow` از `effectiveAmount` استفاده کن (هم برای `countDone` هم برای مقایسهی `>= dailyTarget`).

**توجه:** خواندنِ `prev` باید با `txn` باشد، نه `db`. (وگرنه دوباره dead-lock میسازی.)

**۵-ب) تیک اجندا باید «تکمیل کامل» باشد، نه «۱ واحد».** در `agenda_action_handler.dart` تابع کمکی زیر را اضافه کن و در E-1 استفادهاش کن:

```dart
/// تیک سادهی اجندا = «انجام شد»، نه «یک واحد».
/// شمارش تدریجی فقط از UI اختصاصی مستحبات (تسبیح) انجام میشود.
int _resolveToggleAmount(AgendaItem item, {required bool isDone}) {
  return isDone ? 999999 : 0; // در logDone به dailyTarget کلمپ میشود
}
```

> اگر این عدد بزرگ بهنظرت زشت است، بهجایش `dailyTarget` را از `item` بخوان — **ولی فقط اگر مطمئنی روی `AgendaItem` در دسترس است.** اگر نبود، همین کلمپ را نگه دار و کامنتش را حذف نکن.
> 

**۵-ج) حالت PARTIAL باید در اجندا دیده شود.** در `lib/core/domain/agenda/sources/worship_agenda_source.dart` → `_collectMustahab`، بهجای منطق دوحالته:

```dart
// قبل: چیزی شبیه  completion: status?.isDone == true ? done : none
// بعد:
```

و در `WorshipDayStatus` (فایل `worship_completion_repository.dart`) اضافه کن:

**فراموش نکن:** `AgendaCompletion.partial` تا امروز برای مستحبات **هرگز** تولید نمیشد. بعد از این تغییر مطمئن شو رِندِرِرها این حالت را میشناسند و کرش نمیکنند.

### E-6 — «انجامشده»ی تاریخکور در صفحهی عبادت ← MU-26

**فایل:** `lib/features/worship/logic/worship_engine.dart` → کلاس `WorshipPracticeState`

**مشکل اثباتشده:**

```dart
bool get isDone =>
    resultType == 'DONE' ||
    (countDone >= countTarget && countTarget > 0) ||
    practice.dailyDone == 1;          // ← فاجعه
```

`practice.dailyDone` یک ستون **سراسری روی خود عبادت** است، نه روی تاریخ. `loadDay(anyDate)` همین شیء را برای **هر روزی** میسازد. پس اگر کاربر دیروز یک ذکر را انجام داده باشد (`dailyDone = 1`)، آن ذکر در **همهی روزهای گذشته و آینده** «انجامشده» نمایش داده میشود تا وقتی که یک نوشتن دیگر مقدارش را عوض کند.

بدتر: خودِ `logDone` بالای همان ستون کامنت زده **«Write dailyDone as a write-only cache (never read in business logic)»** — یعنی کد صراحتاً قرارداد خودش را نقض میکند.

همین ایراد عیناً برای `isSkipped` با `practice.dailyDone == -1` هم برقرار است.

**کاری که باید بکنی:**

```dart
bool get isDone =>
    resultType == 'DONE' ||
    (countTarget > 0 && countDone >= countTarget);

bool get isSkipped =>
    resultType == 'SKIPPED' || resultType == 'QADA_ADDED';
```

سپس `grep -rn "dailyDone" lib/` بگیر. **`dailyDone` و `dailyDoneDate` از این به بعد فقط باید در دستورهای `UPDATE` ظاهر شوند، هرگز در منطق تصمیمگیری یا شرط UI.** هر مورد نقض را گزارش کن (ولی خارج از worship چیزی را خودسرانه تغییر نده).

### E-7 — محافظت خطای `_collectMustahab` ← MU-5

**فایل:** `worship_agenda_source.dart`

**مشکل:** `_collectMustahab` تنها collector async بدون `try/catch` داخلی است. یک استثنا (مثلاً `jsonDecode` خراب در `reminderTimes` یک ردیف) کل `agendaForRange` را میترکاند — **نه فقط عبادت، بلکه ورزش و دارو و وظایف کل بازه هم خالی میشوند.**

**کاری که باید بکنی:** حلقهی روی مستحبات را طوری بپیچ که خطای **یک عبادت** فقط همان عبادت را حذف کند:

```dart
for (final p in mustahabPractices) {
  try {
    // ... منطق فعلی برای همین یک عبادت
  } catch (e, st) {
    RitmoLogger.error('WorshipAgendaSource._collectMustahab practice=${p.id}: $e', e, st);
```

**فراموش نکن:** `try` را دور **کل تابع** نگذار — آنوقت باز هم همهی مستحبات با یک خطا ناپدید میشوند. `try` باید **داخل** حلقه و بهازای هر عبادت باشد.

### E-8 — `ONCE` بدون محافظ null ← MU-6

**فایل:** `worship_agenda_source.dart` → `_collectMustahab`

```dart
case 'ONCE':
  final onceDate = p.reminderDaysOfWeek?.trim();
  if (onceDate == null || onceDate.isEmpty) {

      'Mustahab ${p.id}: reminderFrequency=ONCE اما تاریخ ثبت نشده — نادیده گرفته شد',
```

### E-11 — ساعت جعلی و سرریز نیمهشب ← MU-9 + MU-10

**۱۱-الف) ساعت جعلی `'08:00'`:** وقتی عبادت هیچ ساعتی ندارد، کد `'08:00'` میگذارد. نتیجه: `AgendaItem.itemType` به `fixed` تبدیل میشود، آیتم **بالای قرارهای واقعی** مرتب میشود، و ساعتی به کاربر نشان داده میشود که خودش هرگز ثبت نکرده.

**رفع:** `timeOfDay` را `null` بگذار. `AgendaItem` خودش `itemType` را `floating` میکند و آیتم در بخش بدونساعت مینشیند. **هیچ مقدار پیشفرضی جایگزین نکن.**

**۱۱-ب) سرریز نیمهشب در `_resolveAnchorTime`:** برای `BEDTIME 23:30` با `reminderOffsetMinutes = 60`، محاسبه `rh = 24 % 24 = 0` میدهد → `00:30` **همان روز** → آیتم به بالای لیست پرت میشود. آفست منفی هم همین کلاس خطا را دارد (`-30` → ساعت منفی).

**رفع:**

```dart
final totalMinutes = anchorHour * 60 + anchorMinute + offsetMinutes;
if (totalMinutes < 0 || totalMinutes >= 24 * 60) {
  // سرریز به روز قبل/بعد → این یادآور متعلق به این روز نیست
  return null;
}
final rh = totalMinutes ~/ 60;
final rm = totalMinutes % 60;
```

**فراموش نکن:** خروجی `null` باید در فراخوانکننده به «آیتم بدون ساعت» ترجمه شود، نه به حذف آیتم. اگر عبادت روز درستی دارد ولی ساعتش سرریز کرده، باید **بدون ساعت** نمایش داده شود.

### E-12 — چهار معنی مختلف در یک ستون ← MU-11

**مشکل:** ستون `reminderDaysOfWeek` بسته به `reminderFrequency` چهار چیز کاملاً متفاوت نگه میدارد: روزهای هفته / روزهای ماه شمسی / روزهای ماه قمری / یک تاریخ کامل ISO. هیچ تمایزدهندهای وجود ندارد. اگر کاربر فرکانس را از `WEEKLY` به `LUNAR_MONTHLY` عوض کند، مقدار قدیمی میماند و **بیسروصدا بهعنوان روز قمری تفسیر میشود.**

## 🧪 تستهای اجباری (هر ۸ تا؛ هیچکدام اختیاری نیست)

1. **تست dead-lock:** یک عبادت مستحب بساز، از اجندا تیکش بزن، سپس **بلافاصله** یک عملیات دیتابیسی دیگر انجام بده (مثلاً یک روتین را تیک بزن). باید هر دو کار کنند. قبل از E-1 این تست باید hang کند — اگر hang نکرد، یعنی تحلیل غلط بوده؛ **گزارش بده و ادامه نده.**
2. **تست تیک قرآن/ذکر:** یک عبادت `QURAN` بساز، در اجندا تیک بزن، اپ را ریاستارت کن، تیک باید باقی باشد.
3. **تست `dailyTarget > 1`:** عبادتی با `dailyTarget = 3` بساز. از اجندا تیک بزن → باید `DONE` شود و **برنگردد**. از UI تسبیح یکییکی بزن → `countDone` باید ۱→۲→۳ برود، نه اینکه روی ۱ بماند.
4. **تست تاریخکوری:** عبادتی را **امروز** انجامشده علامت بزن، سپس در تقویم عبادت به **دیروز** و **فردا** برو. هر دو باید «انجامنشده» باشند.
5. **تست همگامی کش:** از اجندا تیک بزن → **بدون ریاستارت** به صفحهی عبادت برو → باید تیکخورده باشد. سپس از صفحهی عبادت برشدار → به اجندا برگرد → باید برداشته شده باشد.
6. **تست نوتیفیکیشن ≠ حذف:** `reminderEnabled` یک عبادت را خاموش کن. عبادت باید **همچنان در اجندا باشد**، فقط نوتیفیکیشن نگیرد.
7. **تست انزوای خطا:** عمداً `reminderTimes` یک عبادت را در دیتابیس به یک رشتهی JSON خراب تغییر بده. نمای ماه اجندا باید **کامل** لود شود و فقط همان یک عبادت غایب باشد — ورزش/دارو/وظایف نباید ناپدید شوند.
8. **تست `ONCE` و `LUNAR_MONTHLY`:** یک عبادت `ONCE` با تاریخ خالی بساز (باید غایب باشد + لاگ warning بدهد). یک عبادت `LUNAR_MONTHLY` روز ۱۵ بساز و یک ماه کامل را مرور کن — باید **دقیقاً یک بار** ظاهر شود.
